# M1 — Machbarkeitsuntersuchung

Datum: 29. September 2026. **M1 ist gestartet; das Diagnosewerkzeug ist implementiert und geprüft. Die fachliche M1-Abnahme bleibt wegen offener Lock-/Identitäts- und Hardware-Gates ausstehend. M2 wurde nicht begonnen.**

## Ergebnis

- Ein natives Swift-Package untersucht USB, Power und Benutzersitzung ohne reale Systemaktionen. Es gibt keine Registrierung von Diensten und keine Änderung von Berechtigungen oder Key-Konfiguration.
- Debug-/Release-Build und acht Swift-Tests bestehen. Ein Apple-Development-signierter Release-Probe-Build wurde zusätzlich verifiziert und mit `inspect` gestartet. Keine Developer-ID-Application-Identität vorhanden, keine Notarisierung oder Distribution geprüft.
- Der angeschlossene Yubico-Key wird als `1050:0407` erkannt. In den geprüften passiven Registry-Feldern fehlt eine Seriennummer; der USB-Seriennummerindex ist 0. Das strikte persistente Enrollment bleibt damit für diesen Befund ausgeschlossen.
- Die öffentliche SDK-/API-Prüfung hat weiterhin keinen tragfähigen direkten Lock-/Bestätigungspfad geliefert. Der reine Event-Posting-Preflight war `false`; eine Berechtigung wurde nicht angefragt.
- Ein 120-sekündiger Watch-Lauf endete vollständig ohne Fehler, ohne aufgezeichnetes Removal/Reconnect und ohne reale Aktionen. Die physische Removal-Prüfung ist damit weiterhin offen.

## Umgebung und reproduzierbare Befehle

Apple Silicon (`Mac17,3`), macOS 27.0 (`26A428`), Xcode 27.0 (`27A266a`), Swift 6.4. Die Planung nennt macOS 27.x; dieser Bericht qualifiziert weder andere Patchstände noch andere Geräte.

Vom Repository-Stamm aus:

```sh
export PULLOCK_PROBE_BUILD=$(mktemp -d "${TMPDIR%/}/pullock-probe.XXXXXX")
swift test --package-path tools/hardware-harness --scratch-path "$PULLOCK_PROBE_BUILD"
swift build --package-path tools/hardware-harness --scratch-path "$PULLOCK_PROBE_BUILD" -c release
swift run --package-path tools/hardware-harness --scratch-path "$PULLOCK_PROBE_BUILD" pullock-probe inspect
swift run --package-path tools/hardware-harness --scratch-path "$PULLOCK_PROBE_BUILD" pullock-probe simulate
swift run --package-path tools/hardware-harness --scratch-path "$PULLOCK_PROBE_BUILD" pullock-probe watch --seconds 120
```

Die Logs liegen lokal unter dem ignorierten Verzeichnis `.local/`; sie werden nicht automatisch hochgeladen. Der Report enthält die relevanten bereinigten Befunde. Das Werkzeug puffert JSONL bis zum Ende, verwendet fortlaufende Sequenzen und monotone `mach_continuous_time`-Zeitstempel.

Die acht automatisierten Tests prüfen fehlende/ungültige/widersprüchliche Kennungen; strenge Zahlentypen und Wertebereiche; keine Zusammenführung verschiedener Seriennummern; reportlokale statt globale Tokens; Startup/fremde/doppelte Removal; verworfene Presence über Sleep-/Sessiongrenzen; unterschiedliche Callback-Reihenfolgen; nicht aktivierbare reale Aktionen.

## Gefundene und behobene Probleme

1. Die verschachtelten `IOMessage.h`-Makros sind nicht direkt aus Swift importierbar. Ein kleiner C-Header macht ausschließlich die fünf SDK-Konstanten zugänglich; keine hart codierten Ersatzwerte oder Aktionen.
2. Swift Testing kann einen mutierenden Struct-Aufruf nicht in jeder `#expect`-Expansion auswerten. Mutationen werden vor dem jeweiligen Assert ausgeführt.
3. File-Provider-/Finder-Metadaten im Projektordner ließen die ad-hoc-Signierung des Testbundles scheitern. Ein separates temporäres Buildverzeichnis löst dies, ohne die Signaturprüfung abzuschalten.
4. `IOServiceGetMatchingServices` kann laut aktuellem SDK bei Erfolg einen Null-Iterator liefern, wenn kein Gerät passt. Dieser Fall wird jetzt als leerer Bestand behandelt, nicht als defekter Iterator.
5. Ein Top-Level-`idVendor` im `IOUSBHostDevice`-Matching-Dictionary lieferte auf dem Testsystem trotz angeschlossenem Key keinen Treffer. `kIOPropertyMatchKey` mit `idVendor` findet die richtige physische Instanz. Gegenprobe mit ungefiltertem Matching, Top-Level-Filter und Property-Filter durchgeführt; das Werkzeug liest weiterhin nur Yubico-Kandidaten.

## Offene Gates und nächste Entscheidungen

| Gate | Was noch erforderlich ist |
| --- | --- |
| Sitzungssperre | Unterstützten Request-/Bestätigungspfad belegen oder eingeschränktes Betriebsprofil ausdrücklich freigeben; [DTS-Entwurf](../decisions/apple-lock-question.md) vorbereitet, nicht versendet |
| Individuelle Identität | Für den beobachteten Key passiv nicht vorhanden; Session-Key-Modus oder aktive Herstellerabfrage wären Scope-Änderungen und sind nicht implementiert |
| Reale Ereignisse | Abziehen/Reconnect, Sleep/Wake, Sessionwechsel und Topologien tatsächlich aufzeichnen; keine Qualifikation aus bloßer Subscription |
| Power-Race | Serienverarbeitung beweist keine quellenübergreifende Reihenfolge. Der Test macht den Unterschied sichtbar; Shutdown dafür nicht freigegeben |
| Koexistenz / Support | Physische Matrix einschließlich FIDO/PIV/OTP/SSH prüfen; Modell, Firmware und Anschlussart ergänzen |
| Distribution | Developer ID, Notarisierung, Diensteinstallation und XPC gehören zu späteren Gates |

Keine reale Sperre, kein Shutdown, keine Credential-Abfrage und kein Versand einer externen Anfrage durchgeführt. Die [Supportmatrix](../compatibility/M1.md) weist nicht ausgeführte Hardwareprüfungen ausdrücklich aus.
